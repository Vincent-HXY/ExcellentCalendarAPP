## 1. 计划定位

本计划把底部“搜索”占位 Tab 建设为 Android 优先、Local-first 的独立搜索页面，统一检索：

- Event 与重复 Event 的逻辑对象；
- Habit 习惯定义；
- Anniversary 纪念日定义。

页面提供中文关键字搜索、三类固定分组、业务日期筛选、内容类型与 Category 筛选、完成状态筛选、智能排序、匹配高亮、独立分页、设备本地搜索历史和详情跳转恢复。

本计划不实现联网搜索、云端搜索、AI 语义搜索、拼音搜索、错别字纠正、附件/OCR 搜索、地图地点搜索或跨设备历史同步。

可行性判定：`SPECIALIST_SPLIT`。

原因：需求同时新增统一 Search Contract、跨 Event/Habit/Anniversary 的 C++ 查询与 occurrence 解析、SQLite 查询策略、Kotlin/JNI/MethodChannel 接线、Kotlin 本地历史存储、Dart Gateway/Application 状态和完整 Flutter 页面；还需要为未知数据规模建立性能与 FTS 迁移门禁。它可以实现，但不是一次小型跨层补丁，必须按 Contract/数据、C++/Storage、Kotlin/JNI、Flutter、真实集成/性能和独立 Review 分轨交付。

## 2. 当前仓库基线与启动门禁

### 2.1 已有基础

- 主导航已经是“日程 / 日历 / 搜索 / 我的”四 Tab；`flutter_client/lib/presentation/home/main_tab_page.dart` 中搜索仍为占位页。
- Event 已有生产 `event.search`，可按标题、内容、地点关键字以及时间、状态、Category、Importance、重复和来源过滤。
- Event、Habit、Anniversary 均有真实详情路由；重复 Event 可携带 occurrence identity。
- Habit 已有标题、描述、Category、挑战日期与 lifecycle 投影；Anniversary 已有标题、备注、Category 与 occurrence/countdown 投影。
- 项目已有 `SearchIndex` 领域概念和 `contracts/search/search_index_response.schema.json`，但它只是索引记录投影，不是统一搜索 request/response，也未证明存在可用的生产索引 writer、rebuild 或 FTS。
- Category 已有稳定 `category_id`、当前名称和颜色投影；结构化筛选必须使用 ID，名称仅用于当前显示与全文匹配。
- Kotlin 已有本地 Store 与后台 executor 基础；Search history 因需要 confirmed CAS，Revision 2 固定采用 `AtomicFile + noBackupFilesDir`，不复用 SharedPreferences。
- Flutter 已有主题、外观、四 Tab、详情页、分页、错误状态、Gateway Fake 和 Widget 测试基础可复用。

### 2.2 当前缺口

- 没有 `search.*` 公开 MethodChannel 或 Kotlin→C++ native call。
- Habit 与 Anniversary 没有关键字搜索能力。
- 没有统一的三类 query、分组 response、稳定排序、精确总数或独立 cursor。
- 没有跨字段中文原文匹配、英文 ASCII 大小写不敏感、空格 token AND 的机器验收。
- 没有逻辑对象去重、重复 Event 最近/下一 occurrence 选择和三类统一时间筛选语义。
- 没有搜索历史持久化、长按管理模式、单项删除、清空与撤销。
- 没有 Search 页面 Controller、stale-response 防护、Tab/详情返回状态恢复或完整状态 UI。
- 没有代表性数据量、真实 Android 设备性能基线、FTS tokenizer 选择和 Storage migration 计划。
- 当前工作树包含大量 Habit/Contract/C++/Android/Flutter 在途修改；实现前必须建立可识别基线，禁止覆盖、整理或回滚用户现有修改。

### 2.3 已识别的真相源缺口

现有 `SearchIndex.occurAt/occur_at` 只有 nullable datetime，不能无损表达 Habit 与 Anniversary 的用户本地 date-only 语义。按照当前用户需求和 date/datetime 不变量：

- 新的 Search 查询投影必须区分精确 `occur_at` 与本地 `occur_date`；
- 不得把 Anniversary 或 Habit 日期强行转换为 UTC 午夜；
- 现有 SearchIndex 只能视为可重建派生索引概念，不能直接充当三类结果 Contract；
- 若未来实施 FTS，先由 Contract/数据负责人修订索引时间投影、writer、rebuild、失效和迁移规则。

本计划以用户已确认需求、date/datetime 领域不变量和 canonical Event/Habit/Anniversary 数据为本次 Source of Truth。现有 SearchIndex 不足部分不阻塞计划设计，但阻塞直接启用持久化索引或 FTS。

## 3. 已冻结的产品需求

### 3.1 页面结构与视觉

- 搜索页使用项目主题下的浅色背景、白色大圆角分组卡片和品牌色强调；深色模式使用等价主题 token，不写死截图颜色。
- 无关键字时显示大标题“搜索”；开始搜索后标题平滑收起，搜索框上移。
- 搜索框左侧为搜索图标，中间为中文输入框，输入后显示清除按钮；右侧独立按钮为筛选入口，不显示参考图中的“取消”。
- 筛选按钮存在非默认条件时显示按条件组计数的角标；搜索框下方显示已应用条件标签，标签可单独移除。
- 无关键字时显示“搜索记录”；有关键字时显示搜索状态或三类结果；不得显示“云端搜索”。
- 底部四 Tab 始终保留，搜索 Tab 使用选中态品牌色。

### 3.2 输入与查询触发

- 输入一个或多个非空字符后，以“最后一次输入结束”为起点 debounce `1s` 自动搜索。
- 继续输入、删除或组合输入法仍处于 composing 时重新计时；不得在中文输入法组合文本尚未提交时查询。
- 点击键盘“搜索”立即查询，不等待剩余 debounce；仅在该请求成功后记录 response 的规范化关键字，零结果也记录，失败/取消/stale response 不记录。
- 清空关键字立即取消待执行 debounce、使在途结果失效并返回搜索历史。
- 每个请求携带 generation；旧 generation 返回时不得覆盖新关键字、新筛选或已销毁页面状态。
- 空字符串或仅空白字符不调用 C++ 搜索；第一版不提供“仅靠筛选浏览全部内容”。筛选可以提前设置，输入关键字后生效。

### 3.3 匹配字段

| 类型 | 参与匹配字段 | 不参与匹配 |
| --- | --- | --- |
| Event | 标题、内容/备注、地点、当前 Category 名称 | ID、Reminder、内部 recurrence 文本、来源枚举 |
| Habit | 标题、描述、当前 Category 名称 | CheckIn 技术标识、统计数字、Reminder 模板、单位 |
| Anniversary | 标题、备注、当前 Category 名称 | recurrence ID、倒计时数字、Reminder 技术字段 |

- Category 结构化筛选始终使用 `category_id`；名称仅按查询时的当前 Category 投影参与匹配与展示。
- Category 更名后应按新名称搜索；Category 缺失或软删除时保留目标对象，Category 展示为 null，旧名称不得继续命中。

### 3.4 匹配规则

- 中文使用原文连续子串包含匹配，不做分词词典、拼音、同义词、错别字或语义扩展。
- 英文 ASCII 字母忽略大小写；第一版不承诺完整 Unicode case folding 或重音符号归一化。
- 首尾空白去除，连续空白折叠；按 Unicode 空白拆分 token。
- 多个 token 使用 AND：每个 token 都必须命中，但可以命中同一对象的不同允许字段。
- 历史记录保存规范化后的展示关键字：首尾空白去除、连续空白折叠，保留用户原文字形。
- Contract 子计划冻结最大关键字长度和 UTF-8/Unicode 校验；超限、空白或非法编码返回明确 `SEARCH_QUERY_INVALID`，不得静默截断。

### 3.5 逻辑对象与 occurrence

- 一个 Event/Habit/Anniversary 逻辑对象在一个 section 中最多显示一次。
- 重复 Event 不按全部 occurrence 展开成大量重复行。
- 不限时间时：重复 Event 显示下一次有效 occurrence；不存在未来 occurrence 时显示最近一次过去 occurrence。
- completed recurring Event 适用 Calendar 同源 cutoff：只有 anchor 严格早于 `completed_at` 的 occurrence 存在；不限时间时固定显示 cutoff 前最后一个 eligible occurrence，截止前没有 occurrence 则不返回该 Event。cutoff 前开始的长区间保留完整范围，等于/晚于 cutoff 的 occurrence 不能由显式 state 复活。
- 使用时间范围时：只要存在一个符合状态且与范围相交的 occurrence 即匹配，并展示范围内距离请求 timezone 当地 today 最近的一次；open 不优先于更近的 closed。等距时当前/未来优先于过去，再按当地开始、revision、occurrence key 决胜。
- Event occurrence identity 必须足以进入正确详情；不得仅返回无法反查或会跨 recurrence revision 漂移的裸 UUID。
- Habit 时间匹配使用 challenge 当地日期区间；Daily CheckIn done 只表示当天完成，不把整个 Habit 变为已完成结果。
- Anniversary 时间匹配使用一次性或年度 occurrence 当地日期；不限时间时显示下一 occurrence/countdown，不得把 date-only 转为 UTC 午夜。

### 3.6 时间筛选

筛选提供：

- 不限时间；
- 今天；
- 过去 7 天；
- 未来 7 天；
- 本月；
- 自定义日期范围。

UI 中自定义起止日期均为包含边界。Application 层根据设备 IANA timezone 转换为 Contract 的当地日期半开区间 `[date_from, date_to_exclusive)`：

- “今天”为 `[today, today + 1 day)`；
- “过去 7 天”含今天，为 `[today - 6 days, today + 1 day)`；
- “未来 7 天”含今天，为 `[today, today + 7 days)`；
- “本月”为当地月首到下月月首；
- date-only 运算不得使用会受 DST 影响的本地 `Duration(days)` 推导。
- timed Event 的请求窗口由 C++ 以请求 timezone 的两个当地午夜解析成 UTC instant；DST gap 取 gap 后第一个有效 instant、fold 取较早 instant。timed overlap 使用 `start < queryEnd && end > queryStart`；all-day 使用 civil-date 同构半开公式，覆盖跨午夜和多日。
- Event 的 pending/in_progress/overdue/completed/skipped 与 Calendar Contract 使用同一状态公式；reopen 后由固定 query clock 动态投影。ongoing 距离为 0，未来从开始、过去从结束计算。

### 3.7 筛选面板

- 点击右侧筛选按钮，从右上角弹出类似参考图三的白色大圆角浮层。
- 第一版只包含五组：时间范围、内容类型、我的分类、包含已完成、排序方式。
- 内容类型默认为日程/习惯/纪念日全选，至少保留一类。
- Category 支持多选和“未分类”；空 Category 选择表示不限制。
- “包含已完成”默认开启。
- 筛选浮层使用 staged state；调整期间不查询，点击“查看结果”后一次性应用，另提供“重置”。
- 点击遮罩或系统返回键放弃未应用的 staged state，并保留上次已应用条件。
- Importance、是否提醒、是否重复、来源、地点结构化筛选不进入 V1，因为三类领域含义不一致或只覆盖部分类型。

### 3.8 完成与排除规则

- Event：默认包含 active 与 completed；cancelled、archived、soft-deleted 始终排除。
- 重复 Event：单次 completed/skipped/cancelled 由 occurrence 状态解释；系列仍有未来有效 occurrence 时，逻辑对象仍可作为进行中结果。
- 关闭“包含已完成”后，排除已完成的一次性 Event，以及在当前匹配范围内只有完成 occurrence 且没有有效 occurrence 的结果。
- Habit：默认包含 upcoming、active、completed、ended_early；关闭后只保留 upcoming 与 active。
- Habit 当日 done/partial/skipped/missed/absent 不改变逻辑对象的 lifecycle 完成筛选。
- Anniversary 没有完成状态，不受该开关影响；soft-deleted 始终排除。

### 3.9 分组、分页与数量

- 分组顺序固定为“日程 / 习惯 / 纪念日”。
- 未选择的类型和匹配数量为 0 的 section 隐藏。
- 每组标题显示精确总数量。
- V1 首屏和续页每组固定请求 20 条；每组独立“加载更多”，不得因加载一个 section 重置或重查其他 section 的已显示页。
- 加载更多按 ID 去重；重复、漏项或旧页覆盖新查询均属于阻断缺陷。
- Cursor 必须 opaque、绑定规范化 query、筛选、排序、target type、timezone 和数据 snapshot/generation；以进程级 OS CSPRNG key 的完整 HMAC-SHA-256 认证，constant-time 验签，进程重建后旧 cursor 非法。禁止复用 FNV/Calendar checksum；非法 cursor 与过期 cursor 使用不同错误语义。
- Section cursor 过期时只刷新受影响 section；首次查询失败才进入全页错误。

### 3.10 排序

提供三种排序：

1. **智能排序（默认）**：标题完全匹配 → 标题前缀匹配 → 标题包含 → 标题 token 命中 → 内容/描述/备注 → 地点 → Category 名称；同一匹配等级下，进行中优先、未来时间由近到远、过去时间由近到远、已完成靠后，再以 `updated_at` 和稳定 ID 决胜。
2. **时间最近**：有未来业务时间的结果从近到远，其后为最近过去时间；无业务时间的结果最后；同时间使用稳定 ID。
3. **最近更新**：`updated_at desc`，同时间使用稳定 ID。

- 排序由 C++ Search Query Service 权威实现；Flutter 和 Kotlin 不重新计算相关度或业务时间。
- 相关度分值无需跨层暴露；Contract 只冻结可观察的优先级与稳定排序行为。

### 3.11 结果卡片

- 每个类型 section 使用一张白色大圆角卡片，内部为两到三行紧凑条目和轻分隔。
- 第一行包含类型/状态图标、标题和必要状态；标题最多两行。
- 标题命中时高亮所有可见命中；如果只命中内容、描述、备注、地点或 Category，则显示最多两行的上下文摘要并高亮命中。
- 高亮使用主题适配的琥珀/橙黄色背景与可读前景色；深色模式下必须满足对比度，不依赖颜色表达命中或状态。
- Event 辅助信息显示选中 occurrence 的当地日期/时间、全天标识、地点与 Category 中实际存在且有价值的字段。
- Habit 辅助信息显示 lifecycle、挑战日期/剩余语义、目标摘要与 Category；不得显示 CheckIn UUID 或 recurrence 技术文本。
- Anniversary 辅助信息显示下一/匹配 occurrence 日期、倒计时/已过去语义与 Category；不得显示 recurrence 技术文本。
- 已完成/提前结束条目使用状态图标和弱化文字，不使用影响中文可读性的整行删除线。

### 3.12 搜索历史

- 历史只保存在当前 Android 设备，不同步、不上传、不进入 Calendar Core 业务数据库。
- 最多保存最近 20 个不同的规范化关键字；重复关键字移动到最上方。
- 仅在成功的键盘提交、点击历史或打开某条搜索结果时记录；debounce 自动查询本身不记录半截输入。
- 点击历史立即填入输入框、移动到最上方、排队持久化并执行搜索；该查询后来失败也不撤销这次明确的历史选择。
- 打开结果时使用当前已接纳 response 的 `normalized_keyword` 先排队置顶记录，再立即导航；history 写失败只回滚历史 UI并提示，不阻断查询或导航。
- 默认历史列表不显示逐项删除按钮。
- 长按任意历史记录进入“历史管理模式”，提供触觉/可访问反馈，所有历史项同时显示删除按钮；点击相应按钮删除单项。
- 管理模式下系统返回键和显式“完成”退出管理；删除最后一项后进入空历史状态并退出管理。
- “清空全部”立即清空，并显示短暂“撤销”操作；撤销恢复清空前的完整有序快照。
- 清空后的撤销只对当前 generation 生效；若期间已经新增、删除或再次清空历史，旧撤销不得覆盖新历史。
- 存储损坏、类型不合法或超过 20 条时安全规范化，不崩溃、不泄露原始异常，也不伪造同步成功。

### 3.13 页面状态、导航与恢复

- 搜索状态至少包括：idle/history、debouncing、initialLoading、ready、empty、sectionLoadingMore、refreshing、error、historyManaging。
- 初次 loading 可显示骨架；已有结果时新查询可保留轻量 loading 指示，但旧结果不得被误认为新 query 结果。
- 点击结果进入已有详情页；V1 不在搜索行内编辑、完成、打卡或删除。
- 从详情返回时保留关键字、已应用筛选、已加载分页和滚动位置。
- 详情发生修改或删除时刷新相关 section；无变更返回不重复查询。
- 切换底部 Tab 后在当前进程会话保留状态。
- App resume 时立即重读设备 IANA timezone 与当地 today；Search 页处于前台时最多每 60 秒检查一次，并在当地午夜边界额外检查。timezone/today 变化必须推进 generation、取消在途分页、废弃 cursor；预设日期重算，自定义 civil dates 不变，非空关键字刷新首屏。不得用固定 24 小时 Timer 推导午夜。
- 应用进程完全重启后只恢复设备本地搜索历史；关键字、筛选、结果、分页和滚动恢复默认。

### 3.14 空态、错误与无障碍

- 历史为空：显示“暂无搜索记录”和简短说明，不伪造推荐词。
- 无结果：显示“没有找到相关内容”，有非默认筛选时提供“清除筛选”，不提供云端搜索。
- 首次查询失败：显示可重试全页错误；已有结果刷新失败：保留内容并提示重试。
- 单 section 加载更多失败：只在对应 section 显示重试。
- 筛选按钮、清除按钮、历史管理、删除、清空、撤销、结果行和加载更多均需完整 Semantics、TalkBack 标签和至少 48dp 触摸目标。
- 长按历史必须暴露 TalkBack long-click/custom action；不可只依赖视觉或触觉发现。
- 支持系统字体缩放、中文输入法 composing、软键盘搜索动作、横竖屏/窗口尺寸和浅色/深色主题。

## 4. 建议的 Contract 与调用链

以下能力已经由 `搜索-02`、`contracts/search/search_query_invariants.yaml` 与 Search Schema/fixture 最终冻结；本节若有摘要遗漏，以机器 Contract 为准。

### 4.1 公开方法

```text
search.query
  Flutter → Kotlin → JNI → C++
  SearchQueryRequest → NativeResult<SearchQueryResponse>

search.get_local_history
  Flutter → Kotlin local AtomicFile(noBackupFilesDir)
  EmptyRequest → NativeResult<SearchHistoryResponse>

search.replace_local_history
  Flutter → Kotlin local AtomicFile(noBackupFilesDir)
  ReplaceSearchHistoryRequest → NativeResult<SearchHistoryResponse>
```

- `search.query` 同时写入 `contracts/method_channels.yaml` 与 `contracts/native_calls.yaml`。
- 两个 history 方法只写入 `method_channels.yaml`，标记 `implementation: kotlin_local`，不得虚构 JNI/C++ 调用。
- History 使用“读取完整有序列表 + revision compare-and-replace 原子替换完整有序列表”，由 Flutter Application 编排 record/delete/clear/undo，Kotlin 负责强校验、CAS、revision 上界、AtomicFile durable commit、损坏恢复和 no-backup 路径约束。

### 4.2 查询请求建议

`SearchQueryRequest` 至少包含：

- `query_generation`：Flutter stale-response safe-integer token，response 原样回显，不进入 cursor binding；
- `keyword`：规范化前用户输入；C++ 再执行权威规范化与校验；
- `timezone`：IANA timezone；
- `target_types`：非空唯一数组，值为 event/habit/anniversary；
- `date_from` / `date_to_exclusive`：同时 null 或同时存在的当地 date-only 半开范围；
- `category_ids` / `include_uncategorized`：null+false 不限制、空数组+true 仅未分类、非空数组按布尔值决定是否同时包含未分类；空数组+false 非法；
- `include_completed`：默认 true；
- `sort_by`：relevance/occur_time/updated_at；
- `sections`：本次请求的 section page 描述，每项包含 target_type、固定为 20 的 page_size、nullable cursor。

初次查询发送三个 section request；单组加载更多只发送该组 section request。C++ 在一次只读 snapshot 中返回请求 section，避免 Flutter 发起三条互相漂移的独立领域搜索。

### 4.3 查询响应建议

`SearchQueryResponse` 至少包含：

- 原样回显的 `query_generation`、`timezone`、固定 `evaluated_at` 和 `snapshot_token`；
- `normalized_keyword`；
- `sections[]`，每个 section 包含 target_type、items、total_count、has_more、next_cursor；
- 每个 item 使用 discriminated union，保留公共字段和类型专属导航/展示字段；
- 公共字段至少包括 target_type、target_id、title、`match{primary_field,matched_fields,snippet}`、nullable Category projection、updated_at；
- Event item 区分 nullable `occur_at` 与 `occur_date`，并携带稳定 occurrence navigation context；
- Habit item 使用 date-only challenge/lifecycle projection；
- Anniversary item 使用 date-only occurrence/countdown projection。

Flutter 可以根据返回的 `matched_field`、snippet 和同一规范化 token 做纯视觉高亮，但不得自行判断对象是否匹配、相关度等级或业务时间。

### 4.4 错误与 cursor

- 复用 `SEARCH_QUERY_INVALID` 表达关键字、过滤、时间范围和 section 语义非法；结构性 malformed payload 仍使用 `CONTRACT_VALIDATION_FAILED`。
- Search cursor 分别使用 `SEARCH_CURSOR_INVALID`、`SEARCH_CURSOR_QUERY_MISMATCH`、`SEARCH_CURSOR_EXPIRED`；History 使用 `SEARCH_HISTORY_CONFLICT` 与 `SEARCH_HISTORY_STORAGE_FAILED`，不得借用 Anniversary/Habit 专属错误。
- Cursor 只是不透明分页能力，不是持久化书签；mutation、query、timezone、排序或 Contract 版本改变时允许过期。
- Cursor/snapshot wire 为 `prefix.base64url(payload || 32-byte HMAC-SHA-256 tag)`；key 由 C++ native runtime 每进程以 OS CSPRNG 生成且不持久化，Dart/Kotlin 不解析 payload。
- 单个 response Schema 只负责本消息形状；requested section、累计 total、跨页唯一性、cursor 前进及 timezone/evaluated_at/snapshot 恒定由 request-response pair/cursor-chain semantic validator 与运行时共同强制。
- 过期 cursor 应标为可重试，Application 清空该 section 分页并从第一页恢复。

### 4.5 垂直调用链

```text
SearchPage / filter / history
  → SearchController / immutable SearchState
  → SearchGateway + SearchHistoryGateway
  → typed Dart DTO / MethodChannel adapter
  → SearchMethodHandler
      ├─ query → narrow NativeSearchBridge → JNI → C++ SearchQueryService
      │    → Event/Habit/Anniversary repositories + recurrence/occurrence services
      │    → stable section projections from one read snapshot
      └─ history → AtomicFileSearchHistoryStore(noBackupFilesDir)
  → NativeResult<T>
  → stale-generation validation
  → grouped Flutter rendering / existing detail routes
```

Kotlin 只做 Contract 校验、history local storage 和 JNI 转发；不得实现匹配、排序、状态或 occurrence 规则。Flutter 只编排输入、筛选、历史、分页和展示；不得读取三类列表后自行拼接搜索真相。

## 5. 数据、兼容与持久化策略

### 5.1 V1 查询来源

- V1 先从 canonical Event/Habit/Anniversary/Category SQLite repository 生成只读搜索投影。
- 使用单次 read transaction/snapshot，避免三组来自不同数据时刻。
- 搜索结果和 snippet 是派生查询数据，不写回领域实体。
- 不创建第二套可写 Event/Habit/Anniversary 事实。

### 5.2 SearchIndex 与 FTS

- 当前 `SearchIndex` 概念不等于生产索引已经完成，V1 不因文件存在而假定可用。
- 在性能门禁前，不新增 FTS 表、触发器、第三方 tokenizer 或 Storage writer version。
- 若性能不达标，建立独立 Storage/FTS 子计划，至少冻结：
  - date/datetime 双形态索引投影；
  - canonical 数据与索引的同事务增量维护或可靠 rebuild；
  - Category 更名/软删除后的重建；
  - App 升级、崩溃、损坏和版本不匹配恢复；
  - tokenizer 对中文连续子串、ASCII 大小写和多 token AND 的等价性；
  - SQLite migration、回滚、备份恢复和完整 fixture。
- FTS 索引始终是可重建派生数据，不得成为业务真相源。

### 5.3 History 持久化

- 使用 `Context.noBackupFilesDir/excellent_calendar_search_history_v1.json` 的独立版本化 Kotlin `AtomicFile`；由进程单例 Store 与同一互斥锁拥有。
- 数据只包含最多 20 个有序字符串和必要格式版本，不保存结果、filter、Category snapshot、账号 ID 或云同步标识。
- 写入使用 `startWrite → finishWrite`，异常执行 `failWrite`；只有 durable success 后才发布新内存 committed snapshot。revision 上界的幂等替换零写入成功，变化/修复返回 `SEARCH_HISTORY_STORAGE_FAILED` 并保留原快照。
- `noBackupFilesDir` 不参与 Android Auto Backup/设备迁移；Search 不修改全局备份开关，也不添加指向不存在 SharedPreferences 的排除 XML。
- 当前无旧搜索历史，因此是 additive local format，不需要历史迁移；未来变更必须提供显式 reader/normalization。

### 5.4 兼容性

- 新增 `search.*` 属于 Contract v2 的兼容扩展，不改变现有 `event.search` 行为。
- `event.search` 继续服务现有调用者；统一 Search 不通过偷偷改变旧 response 来复用。
- 新的 Search query/history 方法在 Flutter、Kotlin、JNI/C++ 同一发行版本同步交付，并在真实集成前保持 `planned + blocked`。
- 不修改 Event/Habit/Anniversary persisted facts；若性能阶段决定新增索引，则 Storage 版本和 migration 必须单独评审。

## 10. 风险与控制

| 风险 | 影响 | 控制 |
| --- | --- | --- |
| 当前 SearchIndex 只有 datetime | Habit/Anniversary date-only 被错误解释 | 新 query 投影区分 occur_at/occur_date；FTS 前修订索引 |
| 直接复用三个 list 并由 Flutter 拼接 | 分页、排序和状态漂移 | 单一 C++ SearchQueryService + section request |
| Event recurrence 无限展开 | 卡顿、OOM、漏项 | 有界 occurrence 查询与专用性能测试 |
| Category 名称当外键 | 更名/删除后结果错误 | 结构化过滤只用 ID，名称为当前派生文本 |
| 当前数据量未知 | 方案 B 可能在长期数据下变慢 | 1k/10k/50k 性能门禁，失败后独立 FTS 计划 |
| 过早引入 FTS | Storage migration 与中文 tokenizer 风险 | 未达性能门禁前禁止迁移和临时索引 |
| 1s debounce 与旧响应并发 | 旧结果覆盖新输入 | generation/cancellation/query binding |
| 精确总数增加扫描成本 | 首屏延迟 | 同 snapshot 计数并纳入性能基准；必要时由 FTS 计划优化 |
| History 清空撤销覆盖新记录 | 用户新数据丢失 | history generation，旧撤销失效 |
| 长按管理不易发现 | 用户不知道如何单删 | long-click Semantics、触觉反馈、管理态“完成” |
| Habit 后续开放验证债 | 三类 Search 回归可能暴露边界缺陷 | Habit 已 `integrated + active`；Search 只读 production Store，并在 Track 5 回归开放债场景，不以 Fake 替代 |
| Calendar 与 Search 各建展示模型 | DTO 漂移和重复规则 | Contract 阶段协调公共 projection，不互相依赖页面 DTO |
| 当前脏工作树包含大量在途代码 | 覆盖用户修改 | 分层小 diff、逐文件归属、禁止全量格式化/回滚 |
