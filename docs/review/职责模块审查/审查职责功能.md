# 审查结论

基于当前工作区源码、README、DATA_MODEL、contracts 和测试，我识别出：

- P0：2 项
- P1：4 项
- P2：4 项
- P3：没有值得单独立项重构的对象

项目没有出现全面性的分层崩塌。Flutter 的 MethodChannel 仍集中在 boundary adapter，C++ Domain/Application 没有直接依赖 JSON Storage，Kotlin Contract 也没有依赖 Android API。主要问题集中在少数“中心入口”逐渐吸收了模块内部细节：

1. C++ Contract v2 Boundary 已成为明显 God File。
2. Kotlin MethodChannel 总入口同时承担分发、执行、平台操作和后置调度。
3. C++ 事务状态把全部持久化内部结构暴露给 Application workflow。
4. 两个 Flutter 对象混合了 UI/状态与应用流程。

以下方案都可以设计成 behavior-preserving refactoring；不要求修改 Contract、MethodChannel、JNI、JSON 格式或领域语义。

## [P1][专项研判：不整改，当前设计合理] `recurring_event_transaction.hpp` / `RecurringEventState`、`RecurringEventTransaction`

> C++ 专项复核：裸 vector 的事实成立，但问题定性不成立。`RecurringEventState` 位于 repository abstraction，不是 JSON Storage DTO；它显式表达六 store 同一 transaction/journal 的 Unit-of-Work snapshot。当前 Application 的确需要跨集合查找和维护领域关系，六组 StorePort 只会把同一聚合能力扩散为更大的高风险接口，没有已发生的 representation 变更或调用扩散证明该重构收益。

**当前职责**

- 作为完整 v2 Storage snapshot，公开六类实体集合；
- 向 Application 提供读 snapshot；
- 接收可以任意修改全部集合的 transaction callback；
- 提供 Notification 和 Reminder 的特殊局部 mutation；
- 承担跨 store 原子执行入口。

**问题**

跨 Event、Recurrence、Occurrence、Reminder、Notification、Recovery 的统一事务是有意设计，不能简单按实体拆开。

真正的问题是 Application Service 获得了六个裸 `vector` 的完整可变访问权：[RecurringEventState](/A:/calendar/ExcellentCalendarAPP/cpp_core/include/excellent_calendar/repository/recurring_event_transaction.hpp:18)。Workflow 必须了解持久化集合组织、查找方式和替换方式，新增 store 或调整 representation 会波及所有消费者。

这是聚合事务边界合理、内部结构泄漏不合理。

**代码证据**

- 单一 state 暴露六个 store 的可变 vector：[recurring_event_transaction.hpp:18](/A:/calendar/ExcellentCalendarAPP/cpp_core/include/excellent_calendar/repository/recurring_event_transaction.hpp:18)
- 通用 `Operation` 获得整个可变 state：[recurring_event_transaction.hpp:29](/A:/calendar/ExcellentCalendarAPP/cpp_core/include/excellent_calendar/repository/recurring_event_transaction.hpp:29)
- 同一接口又增加 Notification、Reminder 特殊 callback：[recurring_event_transaction.hpp:30](/A:/calendar/ExcellentCalendarAPP/cpp_core/include/excellent_calendar/repository/recurring_event_transaction.hpp:30)
- Application workflow 中大量 `find_if` 和直接 vector mutation，因此 Application 与 Storage representation 形成事实耦合。

**建议拆分**

```text
RecurringEventTransaction
→ RecurringEventUnitOfWork
   → EventStorePort
   → RecurrenceStorePort
   → OccurrenceStateStorePort
   → ReminderStorePort
   → NotificationStorePort
   → RecoveryBatchStorePort
```

不要拆掉统一 transaction/journal。`RecurringEventTransaction` 继续负责一次性提交、journal、rollback/replay；callback 接收具有窄操作的 UnitOfWork，而不是裸 aggregate state。

**建议调用关系**

```text
Workflow
→ RecurringEventTransaction.execute(operation, ...)
→ RecurringEventUnitOfWork
→ 窄 StorePort
→ 同一个六-store snapshot
→ 同一个 workflow journal commit
```

**行为兼容性**

必须保留：

- 六 store 同一 transaction 的原子性；
- `affected_stores` 和完整 after-state journal；
- prepared/committed replay；
- CAS 调度语义；
- 单模板最多一条 open successor；
- JSON 文件和 storage version 不变。

## [P2][专项研判：不整改，当前 composition root 合理] `native_runtime.cpp` / `RuntimeState` 与全局 service getters

> C++ 专项复核：全局 registry 的事实成立，但当前不是职责缺陷。公开 Boundary 是不携带 runtime handle 的 free function/JNI ABI，进程级上下文必须由 composition root 保存；getter 已在 mutex 下返回窄 `shared_ptr` snapshot，旧 snapshot 的写入能力由 `RuntimeStorageLease::revoke` 撤销。建议的 immutable runtime/module view 仍需要同一全局 holder，并会让端点依赖更宽的模块对象；在 Anniversary/Habit 尚未接入前属于预测性抽象。

**当前职责**

- v1 和 v2 repository/service composition；
- Storage/TZDB preflight；
- RuntimeStorageLease 生命周期；
- 全局 runtime 发布、撤销和锁；
- 所有 Application Service 的 process-global registry；
- 每个 service 的独立 getter；
- storage directory 和 initialization error 状态。

**问题**

Composition Root 理应了解全部依赖，因此依赖多不是问题。问题是它同时是可变全局 Service Locator：新增任何 service 都要修改 state、初始化、发布、header 和 getter；Boundary endpoint 通过隐藏全局依赖获取 service。

当前还不影响功能，但 Anniversary、Habit 等模块接入后会继续增长。

**代码证据**

- `RuntimeState` 保存 v1/v2 全部 repository、transaction、service、resolver 和目录：[native_runtime.cpp:30](/A:/calendar/ExcellentCalendarAPP/cpp_core/src/boundary/api/native_runtime.cpp:30)
- 全局 mutable state 与两个 mutex：[native_runtime.cpp:59](/A:/calendar/ExcellentCalendarAPP/cpp_core/src/boundary/api/native_runtime.cpp:59)
- v2 初始化构建并发布完整服务图：[native_runtime.cpp:164](/A:/calendar/ExcellentCalendarAPP/cpp_core/src/boundary/api/native_runtime.cpp:164)
- 后半部为每个 service 重复提供全局 getter：[native_runtime.cpp:236](/A:/calendar/ExcellentCalendarAPP/cpp_core/src/boundary/api/native_runtime.cpp:236)

**建议拆分**

```text
NativeRuntimeRegistry（唯一全局 holder）
→ NativeRuntimeFactory
→ Immutable NativeRuntime
   → RuntimeServices
   → EventServices
   → ReminderServices
```

保留一个 process-global runtime snapshot，但不再为每个 service 维护独立全局字段和 getter。Boundary 可以先获得一次 immutable runtime snapshot，再使用窄 module view。

**建议调用关系**

```text
runtime.initialize
→ NativeRuntimeFactory
→ 完成全部 preflight 和 initialize
→ Registry 原子发布 Immutable NativeRuntime

Boundary Endpoint
→ Registry.snapshot()
→ EventServices / ReminderServices
```

**行为兼容性**

保持：

- reinitialize 前撤销旧 writer；
- 初始化失败后不留下旧 writer；
- candidate 全部成功后才发布；
- mutex 和 lease drain 行为；
- storage/tzdb error；
- v1/v2 当前兼容入口。

**测试影响**

现有测试覆盖 v2 初始化和失败重初始化清理：[recurrence_core_tests.cpp:649](/A:/calendar/ExcellentCalendarAPP/cpp_core/tests/recurrence_core_tests.cpp:649)、[recurrence_core_tests.cpp:667](/A:/calendar/ExcellentCalendarAPP/cpp_core/tests/recurrence_core_tests.cpp:667)。

还需增加：

- getter 与 reinitialize 并发；
- snapshot 持有期间 writer lease 撤销；
- factory 中途失败不发布部分 graph；
- v1/v2 连续初始化；
- 多次 initialize 的资源释放。

**重构风险**

High。它是 composition root，但涉及全局生命周期、锁和 storage writer 所有权，建议最后处理。

   仅移动内部 endpoint/parser，保留全部公开函数。它是收益最高且不触及 persistence 的重构。

   在 Contract 模块边界稳定后按 Runtime/Event/Reminder/Notification 分 handler；最后再抽 `MutationScheduleHook`，避免一次修改过多行为。

   `_handleSubmit` 的现有 widget tests 较强，适合先建立 `CreateScheduleController/UseCase`。

6. **拆 `RecurringEventDetailController` 和 `AppNotificationBootstrap`**

   先提取纯 Application use case，再保持原 controller 为兼容 façade，避免页面层大面积改动。

7. **~~拆 Storage codec 内部 validator~~（已完成：2026-08-09）**

   只改变内部组织，不改变 store envelope、JSON 或 aggregate validation 入口。

8. **~~先引入 Transaction UnitOfWork，再拆 Workflow~~（C++ 专项研判后不执行）**

   `RecurringEventState` 是 repository 层显式的原子 snapshot；当前没有 Storage representation 变化造成的实际扩散，六组 StorePort 反而会扩大事务接口。

9. **~~拆 `RecurringEventWorkflowService`~~（C++ 专项研判后不执行）**

   当前服务围绕 Event 聚合的一次 operation/transaction；update 的 ordinary/recurring 判定必须在事务内加载 Event 后完成，不应前移到 Boundary。

10. **~~最后处理 `native_runtime.cpp`~~（C++ 专项研判后不执行）**

    当前无 runtime handle 的 JNI/free-function ABI 需要进程级 holder；mutex、窄 `shared_ptr` snapshot 与 writer lease revoke 已显式处理生命周期，module view 暂无可证明收益。

- 修改 Contract schema、方法名或 error code；

- 修改 v1 删除、v2 bootstrap 或 JSON 持久化兼容策略；
