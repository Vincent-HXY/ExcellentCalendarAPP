# Anniversary 全链路测试、架构审阅与未提交代码评审任务

目前 Anniversary（纪念日）功能已经完成开发，Flutter 前端页面上的主要功能可以正常使用，暂未发现明显问题。

现在请不要继续扩展功能，也不要立即进行重构。本次任务的目标是：

1. 对 Anniversary 在 Flutter、Kotlin、JNI、C++ 和本地存储之间的完整实现链路进行系统梳理；
2. 独立设计并执行测试，验证当前实现是否真正正确，而不只是页面表面可用；
3. 检查当前实现是否存在 Bug、逻辑缺陷、协议漂移、重复代码、过度复杂化或职责放错层的问题；
4. 结合 `README.md`、`DATA_MODEL.md` 和 `contracts/**`，检查当前实现是否符合项目既定架构；
5. 审阅当前 Git 工作区中所有尚未提交的 Anniversary 相关改动，包括 staged、unstaged 和 untracked 文件；
6. 在不改变现有产品行为的前提下，给出有证据、可执行、分优先级的优化建议。

本次任务默认是一次：

```text

```

而不是一次直接重构任务。

## 四、Contract 一致性测试

检查以下协议之间是否一致：

```text

```

重点检查：

* MethodChannel 方法名是否完全一致；
* Kotlin JNI 方法和 C++ JNI symbol 是否匹配；
* request / response 字段是否一致；
* `snake_case` 是否在跨语言边界保持一致；
* nullable 字段是否被某一层错误地变成必填；
* boolean、number、array、nested object 是否发生类型漂移；
* enum 是否存在大小写或字符串不一致；
* date 与 datetime 是否混用；
* `NativeResult<T>` 的成功与失败结构是否统一；
* 错误码是否全部来自 `error_codes.yaml`；
* 是否存在 Contract 未声明的临时字段；
* 是否存在 Contract 已声明但某一层遗漏的字段；
* 是否存在一层静默丢弃字段的情况。

如有条件，增加自动化测试，验证示例 JSON 能够：

```text
Flutter serialize
→ Kotlin parse
→ C++ parse
→ C++ response serialize
→ Kotlin return
→ Flutter deserialize
```

并保持字段语义不变。

# 十一、代码冗余和复杂度审阅

请重点寻找以下问题：

## 重复代码

* Flutter、Kotlin、C++ 中重复定义字段；
* 多处手写相同字符串方法名；
* 重复的 JSON parser / serializer；
* 重复的日期格式化和验证；
* create / update 大量复制粘贴；
* 相同 `NativeResult` 包装逻辑多次出现；
* 多个测试重复构造同样 fixture；
* Anniversary 和 Event 之间存在可以复用但未复用的边界设施。

注意：

> 不要因为两段代码看起来相似，就强行抽象成公共基类。

只有在语义稳定、重复真实、抽象能降低维护成本时才建议复用。

---

## 过度复杂化

检查是否存在：

* 一个简单调用被拆成过多没有独立职责的类；
* Interface、Adapter、Facade、Gateway 层层包装但没有替换或测试价值；
* 单个 Anniversary 模块引入新的框架或架构模式；
* 过多泛型、反射或动态注册；
* 为未来可能需求提前建立大量当前无调用方的接口；
* 同时存在两套序列化方式；
* 同时存在两套 Repository 或 Storage；
* 只有一个实现却存在多层无意义抽象；
* 为了避免少量重复而制造难以理解的通用框架。

对每一个“过度设计”结论，需要说明：

```text
当前复杂度来自哪里
它带来了什么实际成本
删除或合并后是否会损失必要职责
推荐的最小简化方案
```

---

## 结构和命名

检查：

* 文件是否位于正确模块；
* 类名是否准确表达职责；
* Handler、Gateway、Bridge、Adapter、Repository、Service、Workflow 是否混用；
* Anniversary 是否有独立窄接口；
* 共享文件是否只做共享职责；
* 是否存在过大的 God Class；
* 是否存在跨模块循环依赖；
* include / import 是否不必要；
* 生产代码是否残留临时调试文件、日志或 TODO；
* 是否存在重复、失效或未使用代码；
* 是否有 generated/build 文件误进入工作区。

# 十二、Bug 审阅要求

不能只做风格审查。

重点寻找可能真正造成错误的情况：

* 请求字段被丢失或改名；
* Kotlin/C++ JNI signature 不一致；
* NativeResult 成功和失败状态不一致；
* `ok=true` 但 `data=null`；
* `ok=false` 但没有合法 error；
* 日期按 UTC 零点错误解释；
* date-only 被转换成 datetime；
* 跨时区导致日期提前或延后一天；
* 更新后 Reminder 仍使用旧日期；
* 删除 Anniversary 后 Reminder 继续触发；
* soft delete 后仍出现在普通列表；
* create 成功但没有真正持久化；
* 更新部分成功；
* Repository 写入失败却返回成功；
* C++ exception 穿过 JNI；
* Flutter 页面重复提交；
* MethodChannel 回调重复；
* Activity 重建后 Handler 重复注册；
* 并发调用造成数据覆盖；

# 八、代码冗余和复杂度检查

需要重点检查以下问题。

## 1. 重复实现

查找：

```text

同一 DTO 存在多个含义近似版本

同一个 NativeResult 被重复包装
重复的错误码映射
重复的排序和过滤
```

注意：

> Dart DTO、Kotlin Contract 和 C++ Boundary 分别存在，不一定是冗余。

这是跨语言边界的必要本土化实现。

只有在职责和语义真正重复、造成多真相源时，才应判定为有害冗余。

## 2. 过度抽象

查找：

```text
只有一个实现却拆出多层空接口
大量只转发一行代码的 wrapper

为了一个简单字段引入复杂 mapper 体系
模板或泛型显著增加理解成本但没有复用价值
```

不要为了“代码看起来高级”而建议继续增加层级。
