# Worktree Architecture Review

## 目标

以当前工作树相对选定基线的最终状态为对象，给出可复核、按严重度排序的架构与完整性发现。Skill 只规定审查方法，不保存项目架构、领域规则、当前状态或测试命令副本。

## 范围与只读边界

- 默认审查相对 `HEAD` 的 staged、unstaged、untracked、删除、重命名和冲突文件；用户指定的基线或路径范围优先。
- 不修改生产代码，不执行 stage、commit、reset、restore、checkout、clean、stash、rebase 或历史改写。
- `docs/log.md` 是项目级强制追加记录例外。
- `test_note/**` 是设备或模拟器验收记录例外；仅在本次审查实际完成对应验收后，按 `AGENTS.md` 新增通过环境记录。
- 临时验证产物必须唯一、可追踪；只删除本次审查创建的精确目标，不删除未知文件。
- 记录初始 Git 状态，并在结束时比较，保护用户现有修改。

可使用 `scripts/collect_review_scope.py` 收集只读范围；通过当前环境可用的 Python 入口执行。脚本不可用时，使用等价的只读 Git 状态、diff 和 untracked 文件检查。

## 强制项目导航

冻结审查规则前，按顺序读取：

1. 生效的 `AGENTS.md`；
2. `docs/architecture/overview.md`；
3. 明确用户要求、验收标准、基线、审查路径和范围外内容；
4. `docs/index.md`，据此定位与变更直接相关的 Domain、Accepted ADR、Active Plan、Machine Contract、状态、问题、Active Review 和验证入口；
5. 公开接口、构建边界、实现 diff 和相关测试。

Source of Truth 和冲突裁决严格遵循 `AGENTS.md`。README、历史计划和代码模式只是低优先级证据，不能作为默认架构基准。

## 审查纪律

- 每个 finding 必须包含变更位置、当前权威规则、观察事实、实际影响、置信度和最小修复方向。
- 跨层或跨语言修改只是审查触发器，不自动构成违规；先确认必要性、owner、依赖方向和 Contract 证据。
- 区分事实、推断、不确定性和环境限制；不把文档冲突伪装成确定的代码缺陷。
- 现有测试不是验收标准本身。测试 oracle 应来自用户目标、当前权威规则、公开接口和可观察行为。
- 不报告纯风格偏好、重复根因或没有具体后果的抽象风险。

## 工作流

### 1. 冻结审查清单

- 建立变更清单：路径、Git 状态、模块/层、预期职责和与任务的关系。
- 同时有 staged/unstaged 变化时区分工作树状态与实际提交状态。
- 对相关规则记录来源、适用范围、强制程度和置信度。
- 先读取需求、公开 Contract 和测试入口，再审查实现细节，避免由实现反推预期。

### 2. 审查实现

按当前任务适用性检查：

- 架构责任、依赖方向、公开/私有边界和 production composition；
- 用户目标与实际改动的范围闭合，是否混入无关重构；
- Contract、调用者、适配器、变体、错误、取消、资源、数据、迁移和构建登记是否完整；
- 正确性、安全、并发、性能、生命周期、兼容和失败恢复风险；
- 测试是否覆盖需求与关键负面场景，是否把 Fake/Mock 误报为真实链路。

变更跨多个层、语言、Schema 或运行时边界时，再读取 `references/cross-layer-checks.md`，只应用相关章节。

### 3. 独立验证

验证必须与变更风险相称：

- 文档、配置或静态边界审查可以使用路径、引用、Schema、diff 和一致性检查，不强制编写产品测试。
- 行为或 Contract 变更应冻结独立的正例、边界和失败 oracle，并优先运行已有公开测试入口。
- 只有独立测试能显著增加置信度时才创建临时测试；优先使用隔离目录或不修改生产构建清单的方式。
- 不安装/升级依赖或改变环境配置，除非用户明确授权。
- 失败结果必须区分产品缺陷、oracle 错误、测试工具问题、环境限制和既有失败。

无法安全执行验证时，说明准确原因和仍可执行的静态证据，不制造未运行的通过结论。

## 严重度

- `P0`：数据损失、安全灾难或不可恢复的发布阻断。
- `P1`：明确的正确性/公开 Contract/架构边界破坏或主体实现缺失。
- `P2`：具体且显著的兼容、范围、耦合、测试或维护风险。
- `P3`：低风险但可行动的缺陷；省略纯样式意见。

高置信度需要直接规则与变更证据、确定性静态冲突或可复现失败。低置信度通常放入不确定项而不是 finding。

## 交付

先报告 finding，再给出：

- Verdict：`CHANGES REQUIRED`、`PASS WITH RISKS`、`PASS` 或 `BLOCKED`；
- 审查基线、范围和实际使用的权威资料；
- 架构/边界与完成度结论；
- 实际验证命令、结果、临时产物和状态比较；
- 剩余风险；
- 最后一节列出不确定性和假设。

若没有可行动问题，明确写明。审查结束向 `docs/log.md` 追加记录；本次实际完成设备或模拟器验收时，可新增对应 `test_note/**` 记录，但不修改被审查的生产内容。
